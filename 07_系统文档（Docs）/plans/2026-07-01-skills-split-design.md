# Skill 原子化拆分设计

**日期**: 2026-07-01 | **状态**: 已实施

## 动机

解决巨石 skill（根 SKILL.md 252 行 + 随手录 803 行）的两大痛点：
- **维护/迭代麻烦**：改一个小功能要在几百行里找位置，怕影响到别的逻辑
- **触发不够精准**：巨石加载后内容混杂，容易误触或漏触

## 原则

1. **零功能丢失**：每个原子 skill 的合并 = 原巨石全部内容
2. **每个 skill 只做一件事**：职责单一，触发精准
3. **每个 skill 顶部的纲要**：AI 加载后第一眼知道该不该用、怎么用
4. **外显交互协议**：每个 skill 写明「触发」「输出」「后续流程」

### 数据流

```
用户输入
  │
  ├─ 带 # 前缀 → ②yushu_01_输入解析引擎_Router → 标准化字段 → ⑤飞书操作 → Base/任务
  │                                   ├ #精力 → _energy_status.json → ⑥排程
  │                                   ├ #配置 → _schedule_config.json → ⑥排程
  │                                   ├ #孵化 → 读灵感库 → ⑤飞书操作
  │                                   └ #复盘 → 读执行库 → 返回报告
  │
  └─ 无前缀 → ③意图分类 ─→ 字段齐 → ⑤飞书操作
                           ├ 字段缺 → ④问答校准 → ③意图分类 → ⑤飞书操作
                           ├ 精力 → ⑥排程（调时长）
                           └ 闲聊 → 直接回复（不写库）

⑦多Agent协作 ← 任何写操作前检查责任人
```

## 优于巨石之处

1. **精准触发**：每个 skill 只在一类输入下加载，减少误触
2. **隔离迭代**：改提醒规则只改飞书操作，不影响意图分类
3. **可组合**：问答校准可以被任何流程调用
4. **易排查**：出问题直接定位到对应 skill，不用翻几百行
